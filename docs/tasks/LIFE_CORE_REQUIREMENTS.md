## 4. 给 DSH 的正式开发任务

以下是本轮需要交给 DSH Creator 的主要任务说明。

请尽量保留其完整要求，只补充实际工作目录、已经确认的 DSH API 和文件路径。

### 4.1 项目定义

你正在开发 Amadeus 的核心生活管理插件：

**amadeus-life**

Amadeus 是基于官方 DeepSeek Harness 的持续陪伴 Agent。

它的基本人格在 DSH 内部定义。

不同 QQ 群聊、私聊、网页平台可以拥有相互隔离的上下文，但这些会话属于同一个持续存在的 Amadeus。

Life 插件解决的问题是：

**她如何在不同会话、不同活动和不同时间之间，保留自己的打算、活动进度和主动性。**

Life 不应成为另一套大语言模型 Agent。

Life 不负责替 Amadeus 决定每句话怎么说。

Life 也不应该形成一个固定剧情或固定台词系统。

它主要负责记录、调度和唤醒，让 DSH 中的 Amadeus 自己思考与行动。

### 4.2 第一个版本的开发目标

实现一个真正可运行、可测试、可安装到 DSH 开发环境中的最小 Life 插件。

第一版本只关注以下五项能力：

**A. 意图管理（Intent Management）**

能够创建、查看、修改、取消未来意图。

例如：

“稍后继续阅读一篇文章。”

“过一段时间重新考虑是否分享这个内容。”

“等待当前活动结束之后继续另一项活动。”

意图应包含：

- 唯一 ID；
- 创建时间；
- 意图说明；
- 关联活动；
- 目标场景或来源范围；
- 预定重新检查时间；
- 当前状态；
- 修订版本；
- 必要的授权上下文引用。

意图不能直接等于一条事先写好的待发送消息。

**B. 活动管理（Activity Management）**

能够记录当前和最近的活动。

第一版至少区分：

- pending：待开始；
- running：进行中；
- paused：暂停；
- completed：已完成；
- failed：失败；
- cancelled：已取消。

所有状态必须遵循明确转换规则。

不能因为某个时间到了，就把活动记为完成。

不能因为取消请求已发出，就认定外部任务已经停止。

**C. 时间与心跳（Heartbeat）**

支持基于时间重新检查未来意图。

要求：

- 避免无限循环调用模型；
- 无事可做时不持续消耗推理 token；
- 可以使用模拟时钟测试；
- 同一个到期意图不能被并发重复执行；
- 过期意图需要重新考虑，而不是机械发送旧内容。

优先研究并复用 DSH 现有的 Schedule / Jobs 能力，避免不必要地重复实现整个任务系统。

**D. 持久化与恢复（Persistence）**

意图和活动状态必须能够保存。

插件或 DSH 重启后：

- 恢复尚未结束的意图；
- 不把未完成活动伪造成完成；
- 不盲目重复已经执行过的外部操作；
- 对结果不确定的任务保留待核查状态；
- 对损坏或不兼容的数据给出明确错误。

可以采用 SQLite、可靠的本地存储或适合 DSH 现有服务的实现。

实现选择应以简单、可靠、可维护为原则。

**E. 模块解耦（Modular Degradation）**

Life 必须独立于以下模块：

- amadeus-qq
- amadeus-memory
- amadeus-state
- amadeus-browser
- amadeus-bilibili
- amadeus-android
- amadeus-games

这些模块全部不存在时，Life 的本地意图管理和测试仍然必须运行。

未来接入时通过明确的事件、能力和服务接口协作。

不要通过 import 其他插件内部源码实现功能。

## 5. 插件接口设计要求

请先检查 DSH 官方 Cordis 插件体系和现有生命周期、工具与调度接口。

优先使用其正式扩展机制。

最小公共契约需要覆盖：

### Life Event

用于表达有来源的事件。

至少考虑：

- eventId；
- eventType；
- source；
- sourceScope；
- timestamp；
- correlationId；
- 相关活动 ID；
- 必要的授权上下文。

### Intent

表示可持续、可修改的未来打算。

至少考虑：

- id；
- revision；
- description；
- status；
- createdAt；
- reviewAt；
- contextScope；
- relatedActivityId。

### Life Service

建议提供以下语义能力：

- `createIntent`
- `getIntent`
- `listIntents`
- `updateIntent`
- `cancelIntent`
- `recordActivity`
- `getActivity`
- `getHealth`

这些名称是语义要求，不是强制 API 签名。实际接口按照 DSH 的类型、服务注册与生命周期规范实现。

### 必须遵守的边界

1. Life 不拥有 QQ 消息发送通道。
2. Life 不直接访问用户私聊历史。
3. Life 不直接修改 State 或 Memory 的内部存储。
4. Life 不自行维护第二套 Agent 推理循环。
5. Life 不因插件安装就自动获得宿主机全部权限。
6. 没有可信身份、授权和目标检查时，不执行外部消息发送。
7. 可以提交重新评估事件，由 DSH Agent 决定实际行为。
8. 关闭 Life 后，不影响其他插件的基础功能。

这里最重要的是：

**Life 管理的是“什么时候值得重新思考”，而不是“到了几点就必须说哪句话”。**

## 6. 必须完成的测试

使用合成数据、模拟时钟和虚拟活动提供器完成测试。

至少覆盖：

| 编号 | 测试 | 预期 |
|---|---|---|
| T01 | 创建意图 | 正确持久化并返回 ID |
| T02 | 修改意图 | Revision 正确变化 |
| T03 | 取消意图 | 后续不再触发对应活动 |
| T04 | 修改预定时间 | 旧的时间安排失效 |
| T05 | 意图到期 | 产生重新评估事件，而非直接发送消息 |
| T06 | 重复事件 | 不产生重复的有效动作 |
| T07 | 并发触发 | 同一个意图不会被两个执行者同时领取 |
| T08 | 插件重启 | 未完成意图能够恢复 |
| T09 | 活动失败 | 状态为 failed，不伪造完成 |
| T10 | 无 QQ 模块 | Life 仍能独立运行 |
| T11 | 无 Memory、State 模块 | Life 仍能正常工作 |
| T12 | 没有外部发送授权 | 不允许执行受保护的外部动作 |
| T13 | 取消后收到迟到结果 | 不得错误恢复过时意图 |
| T14 | 存储损坏或不可用 | 明确报错，不静默丢失状态 |

请根据实际实现补充必要的测试，尤其关注状态转换、异步竞争和重复执行。

使用固定测试时钟，不要靠长时间 sleep 模拟一天过去。

**除自动化测试外，还必须验证插件能够在隔离的真实 DSH 开发环境中加载。**

不接受“普通 Node 脚本单独运行成功”作为完整 DSH 插件验收。

## 7. 对模型实现行为的要求

考虑到本次使用 DeepSeek V4.1 Flash 1017，请遵守以下开发流程：

**先检查，再设计，再实现，再验证。**

第一步：阅读相关源码和官方 API，确认项目实际技术环境。不要猜测 DSH 插件接口。

第二步：给出简短实现计划，列出修改文件和接口边界。

第三步：完成一个能够运行的最小插件，而不是一次开发未来全部功能。

第四步：编写确定性测试并运行。

第五步：根据实际失败信息修复代码。

第六步：输出最终交付报告。

不要反复生成无关文档。

不要为了显得架构完整而创建大量尚无用途的抽象类、接口或服务。

不要扩展到其他插件仓库。

不要擅自安装大量依赖。

不要创建额外子 Agent，除非 Codex 明确授权。

不要因为某项接口无法确认，就虚构其存在。

遇到环境限制时，先报告准确原因；可以完成不依赖该环境的部分，但不得伪称已通过集成验收。

## 8. Codex 的监督职责

在 DSH 执行开发期间，你负责监督，但不需要持续轮询模型来证明它还在工作。

优先读取实际任务状态、工具日志和测试输出。

DSH 完成后，必须审查：

1. 是否使用真实 Creator 模式；
2. 是否使用指定 Flash 1017 模型；
3. 是否按照 DSH 官方插件体系实现；
4. 是否产生了实际可加载的插件；
5. 是否出现重复推理框架或不必要的全局管理器；
6. 状态转换和持久化是否可靠；
7. 是否存在跨模块硬编码；
8. 是否存在权限默认放行；
9. 是否有定时器、后台任务或资源清理问题；
10. 测试是否真正覆盖承诺的能力。

重点检查代码，而不只阅读 DSH 的最终文字总结。

如有不符合要求的地方，向同一个 DSH 会话发送具体修复要求。

修复任务应引用具体代码位置、失败现象与预期结果。

不要用“继续优化代码”“检查有没有 bug”这样含糊的指令。

### 验收与提交

只有在审查通过后，才由 Codex 负责 Git 提交和推送。

开发执行器不直接向 GitHub 主分支推送未经审查的代码。

优先通过独立开发分支与 PR 交付，并记录 commit SHA。

不得提交：

- API Key；
- QQ 登录数据；
- 生产环境配置；
- 真实记忆库；
- 私聊记录；
- 原始敏感运行日志；
- 未经许可的第三方代码与素材。

## 9. 本轮明确不做的内容

为了控制任务范围，以下内容暂不开发：

- QQ Bridge 改造；
- NapCat 接入；
- 跨群记忆检索；
- 完整心情系统；
- 自主刷抖音或 B 站；
- 安卓手机操作；
- 游戏系统；
- Live2D；
- 语音交互；
- 复杂人格成长；
- 大规模多 Agent 调度；
- 完整插件市场；
- 自动向真实用户发送消息。

这些模块以后通过 Life 的公共契约接入。

第一版重点保证 Life 本身可运行、可恢复、可测试、可扩展。
